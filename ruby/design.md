+ Threads, coroutines? Syntax for both is still an open question.
+ Introduce `[:Identifier, '?']` as a type that can be nil.
+ Multiline strings with `"""/"""`? Not implemented — `"""hi\nthere"""` today just lexes as three separate adjacent strings (`""`, `"hi\nthere"`, `""`), not one multiline literal.
+ `@splatr` (read-only splat) reads like the identifier itself becomes constant, but it only becomes read-only through that splat. Consider a clearer name: `@splat_read`/`@splat_write`, or `@splat_readable`/`@splat_writable`.
+ Leading idea, may replace the positional-stack-climber idea below: repurpose `./`/`../`/`.../` as project-tier scope operators, old-school style. `./` reaches the current project's own global scope (first-party). `../` reaches into `2nd/` at the project root (second-party libraries). `.../` reaches into `3rd/` (third-party/vendored code, potentially non-language code once FFI exists). Only three fixed tiers, not open-ended chaining. A different axis from the stack-climber idea below — module/dependency-tier resolution, not runtime call-stack depth — so it likely belongs in `@load`/file-resolution, not `scope_for_identifier`. Does not conflict with `self`/`Self`, which stay the instance/type accessors either way.
+ Mechanism for the tiers above: a class-level `second_party_scope`/`third_party_scope`, each its own Global instance, not shared with the user's own — same anchoring pattern `@stdlib_scope` already uses. `../Ident`/`.../Ident` would pull a single identifier straight out of that scope (`tool1 := .../Tool` reaches into `3rd/tool.code` for `Tool {}` with nothing else loaded); a bare `@load '3rd/tool.code'` would still load the whole file, and `x := @load '3rd/tool.code'` would still namespace it under `x`, the same as `@load` already works today — `../`/`.../` would be a third, narrower option alongside those two, not a replacement for either. Not implemented — only `@stdlib_scope` exists today.
+ Open question: like the stdlib (reachable via a bare identifier through Global's readable-scope fallback), should 2nd/3rd-party scopes stay reachable by bare identifier too, or only through the explicit `../`/`.../` prefix? The sandboxing goal seems to need the latter — a 2nd-party library's `Tool` should not silently shadow or collide with the user's own `Tool` just by being loaded.
+ Ties into "Opaque scopes" (not yet designed): full sandboxing needs isolation in both directions. One direction is user code reaching *into* 2nd-party internals only through the explicit pull above. The other is 2nd-party code itself reaching *out* to the user's global through its own `~/` while it runs. `~/` today is always `stack.first`, unconditionally — opaque scopes would need `~/` (and anything else assuming one single global) to resolve relative to whichever sandbox is currently executing, not always the same fixed one.
+ Candidate mechanism for the "opaque" direction (2026-08-19): still one single `stack`, not two swapped ones. A whole second-party stack pushes onto it as one unit, so the array can hold a mix of plain scopes and pushed sub-stacks, e.g. `[Global, [Seconds_Global, ...], <current_scope>]`. The real rule is a search-time guard, not an activate/deactivate step: a `Global` is a hard wall — reverse search (`find_in_stack`, `scope_for_identifier`'s bare-identifier case, anything walking `stack.reverse_each`) stops the instant it crosses any Global, never past it. So from inside second-party execution, search climbs its own frames up to *its* Global, but never falls through to the user's outer Global underneath. Today this rule is vacuously already true, since there is only ever one Global, always at index 0 — nothing regresses; it only starts doing real work once a second Global can exist mid-stack. A later, cross-boundary call (user code holding a reference to a 2nd-party instance, calling a method on it after the fact, with the pushed sub-stack long gone) works the same way an ordinary instance method call already pushes `func.enclosing_scope`'s Instance/Type chain before running — a Func/Type declared inside a realm remembers that origin the same way it already remembers its enclosing Instance/Type, and calling it pushes that realm's stack too, one more link on a chain that already exists.
+ Older idea, superseded by the tiered-scope idea above unless revisited: `./`/`../` as positional stack climbers (`./` = current frame, `../` = one up, chainable) instead of role-based — pure lookup, no auto push/pop, hands back a Scope to `@push_scope`/`@pop_scope` yourself. Phase 1: only real pushed frames climb (func/type/instance/for); `if`/`while`/`until` stay flat like today. Phase 2 (later): give `if`/`while`/`until` their own frame too, reconciled with the Declarator's conditional-flattening. Also decide: climbing past the bottom of the stack should error, not return nil.
+ How can a type mark itself optional or required? `Type?` could mean "it or nil"; `Type!` could mean "must be Type". `?` and `!` are already legal at the end of an identifier — they just carry no meaning yet for a capitalized (`:Identifier`) type name; `Number?` today just lexes as the literal name `"Number?"`, nothing more.
+ Annotate an expression as `Expression` type, e.g. `x: Expression = run.some.piece_of_code()`, giving back the AST of that expression as real instances of its own node types (`Infix | Expression {}`, etc). Related to the AST-exposure idea in todos.md.
+ Formalize what "zeroed" or "nil'd" means for any type. Today `x: Int` reads back `nil` right after declaration — confirmed still true — but arguably should read back `0`; a String should default to `""`. Maybe a `default_value(;)` any class/type can declare. (Asked twice, same question: "What should the default value for an uninitialized declaration be?") Note: calling a bare constructor already gives a sensible default (`Number()` -> `0`, `String()` -> `""`, `Array()` -> `[]`, per todos.md) — this is specifically about a bare `x: Type` declaration with no value, which still reads back `nil`.
+ Enums are `:IDENTIFIER [ ]` whose members are other `:ENUMS [ ]` or `CONSTANTS`. Should be reachable by dot access as long as the left side knows the enum, so it can iterate it: `x: ENUM = ENUM.ABC` becomes `x: ENUM = .ABC`. The "as long as the left side knows the enum" part of dot-access resolution is still hand-wavy.
+ Idea: do not crash on division by zero — return a type that represents infinity instead. `Inf := Infinity | Number`, and `-Inf`. Cannot implement sensibly without deciding how it participates in arithmetic and comparison first (does `Inf <=> 5` work? does `Inf == Inf`?). Needs research. Confirmed still crashing today: `5 / 0` raises a raw Ruby `ZeroDivisionError`, not a language-level error.
+ `lang/number.code`: `denominator` is vestigial across `Number` — every arithmetic operator (`+`/`-`/`*`/`/`, etc.) and comparison operator (`<=>`/`<`/`>`/`<=`/`>=`) only ever looks at `numerator`. A real fix needs every operator to agree on what a `Number` actually means (true rational via cross-multiplication for comparison, fraction-preserving arithmetic, or auto-reduce), not a one-operator patch. Left as-is on purpose for now: `<=>`/`<`/`>`/`<=`/`>=` are the canonical example of `@operator` usage, kept simple.
+ Research how other languages actually treat their Number type (int/float/rational split? one unified numeric tower? how does denominator/rational representation work, if at all?) before deciding what `Number`/`numerator`/`denominator` should really mean here.
+ Decide on an error-handling philosophy. Ruby's exception style is the familiar choice. Tsoding's style — an API that gives back an error message or a bool, e.g. `result, ok := some_thing()` — is also appealing. Related: no try/catch exists at all today; an unhandled runtime error crashes the program outright. Internally, every runtime error is already a Ruby exception, so the interpreter would only need to catch one and hand off to a user-defined handler. Matters most for web routes, file I/O, and DB calls.
+ Ability to pick a member by its type when a name collision shadows it. Repro, still true today: `dict := {keys: 4}`, then `dict.keys()` raises `Receiver_Is_Not_Callable`, since the `keys` member (value `4`) shadows the built-in `keys` function. Idea: `keys: Number = dict.keys` vs. `keys: Func = dict.keys`, picked by the declared type.
+ Jai uses `=` for passing named arguments; this language uses `:=`, which does not quite make sense by analogy. Fine for now.
+ A member can be marked private with a leading underscore, but there is no way to mark a whole expression private.
+ Statements are a step toward making the language buildable in itself. Eventually every class and type could be ported to run in the language itself, with any expression buildable and evaluatable from within the language.
+ Direction: use Structs (Member-backed, `lang/struct.code` + `lang/member.code`) as the common schema mechanism across Database/Table, Server, and Dom, toward one idiomatic way of doing web development instead of ad-hoc per-feature conventions. `structure_declaration` already lets any type declare a structure via the existing `<...>` syntax (`Post<title: String, body: String> | Table {...}`), so no new grammar is needed to start. The Database/Table side has come a long way already: a schema is a named Struct, and query results come back as real Structs (`row_to_struct`), not raw Dictionaries. Server and Dom have not caught up yet: no typed request/response bodies for routes, no declared prop structs for Dom components (still bare instance members). Blocked on: a Database-side bridge translating a Struct member's Type object to a Sequel column type string (partly done — `connection` is now typed `Sequel_Sqlite_Database`, but that is still an empty marker type with no real behavior); and the `@declare <struct>` directive, for stamping a struct's members onto `self` ergonomically (this exists now, but only works correctly outside `Self(;)` — see the `@declare` bug in bugs.md).
+ `ruby/interpreter.rb`: builtins are not user-extensible yet. Requirements likely include: (1) creating a new Type in the language; (2) creating a proxy class in `scopes.rb`, or better, its own file; (3) a function using `@ruby` in its body needs a matching Ruby method named `proxy_#{func_name}`.
+ `@valid_call?` directive: check whether a call would type-check without actually invoking it, e.g. `@valid_call? identity(123)` => `true`, `@valid_call? identity("1")` => `false`. Return-type syntax now exists (`param_types`/`return_type` are both on a real `Func`), so this just needs the directive itself, checking arg count/types without invoking the call. Not implemented yet.
+ Related idea, tabled for now: an operator to structurally match a function's param signature against a shape, e.g. `add ==== {Number, Number;}`. Distinct from the AST-type-check operator already added (`func(;) === (;)`, see todos.md) — that checks an expression's own AST node type, not a function's param/return signature. Does not parse today.
+ Structural typing via `<...>` (Struct) used as a type annotation instead of attached to a type name: `funk { a, b -> <id: Number>; ... }` would mean "returns anything with at least an `id: Number` declaration", checked structurally against the value's own declarations, not against a registered Type's name. Distinct from the existing meaning of `<...>` right after a type name (`Abc<Number>`), which stays "structure of `.tag`" — same syntax, meaning decided by position. Decisions so far: (1) duck-typing against actual declarations is intentional — a plain `{id: 5}` Dictionary should satisfy `<id: Number>` too, not just instances of a matching Type; (2) a Func-shaped member meaning "must respond to X" (interface-style) is a good later idea, not now — data-only for now; (3) runtime-only enforcement for now (reuse the existing return-type `Type_Contract_Violation` check path), not the static Type Checker. Grammar sites in `ruby/parser.rb` that only accept a bare `:Identifier` today and would need to accept a `<...>` literal too: `parse_func`'s inline `-> Type` return type; `parse_func`'s own param `: Type` annotations (named params, and bare-signature-style params); `parse_signature_literal`'s param types (same two shapes); `parse_identifier_expr`'s general `: Type` annotation (variable declarations, e.g. `x: Number = ...`) — this last site already has a `: <...>` grammar path today (stored, never enforced) that this would need to reconcile with rather than duplicate.
